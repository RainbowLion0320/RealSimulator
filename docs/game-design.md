# 大明王朝1582：设计讨论

更新日期：2026-09-24

## 当前实现进度

已进入第一版实现：手机竖屏网页与 Android APK，共用同一个确定性数值引擎。下文保留原有共识与完整设计目标；候选方案不表示全部已经实现。具体首版范围、数值标定与局限见 [数值模型](NUMERICAL-MODEL.md)，交付验证见 [QA](QA.md)。

最新确认：游戏正式命名为 **大明王朝1582**。奏折、召见、执行回报使用现代中文，保留陛下、内阁、户部、诏令等关键词体现时代。已有存档的旧措辞可迁移，但数值与既有决定不变。

首版开局日期暂采用 1582 年七月一日，每月三十日的模拟历法；人物与 UI 以已看过的手机竖屏、人物概念图为实现参考。以上历法和区域粒度是实现选择，不追记为用户明确确认的历史细节。

## 一、已确认的方向

以下来自用户的初始要求及后续回答。

1. 做一个强调真实感的王朝模拟器，以明朝皇帝的视角展开。
2. 玩家不拥有俯瞰国家的全知视角。皇帝主要通过大臣、身边人提供的信息，以及自己的有限观察了解世界。
3. 表面数据本身可能不准确：皇帝收到的账目、粮额、兵额等数据可以与地方实际状态不同。此差异是核心模拟机制，不能仅用几段“有人瞒报”的剧情表现。
4. 通过持续、深入的讨论敲定游戏细节，随讨论逐步落实到文档。
5. 在本地建立 Git 仓库，并同步到用户的 GitHub。
6. 从真实历史节点开局，之后允许改变历史走向。已确定为 **1582 年（万历十年），张居正去世后、万历亲政**；用户接受以亲政代替即位作为开局。
7. 奏折批示与召见追问两者都重要，允许玩家自己选择怎样当皇帝。
8. 开局体验定位为从盛转衰的节点，让玩家体会帝国如何走向衰落。1582 年作为中兴之后的设计起点，不将其说成明朝各方面公认的整体峰值。
9. 不通过自由打字与角色对话，不依赖运行时大模型调用；使用非常丰富的预设文案和系统选项。
10. 数值体系必须具有合理性，并支撑实际状态与呈报数据之间的差异。
11. **正常游玩时，系统不替玩家判断真伪。** 不展示可信度、腐败度、真实忠诚度等皇帝无法直接获知的评分、标签或结论。内部可以按需要采用评分模型，也可以不用；尚未确定内部实现。结算的数据公开例外见第 26 条。
12. 查验所得仍是查验者的报告，不自动成为系统认证的真相。玩家通过信息来源、具体内容、见闻和反馈自行判断。
13. 皇帝去世后允许继续扮演继任者，延续同一局王朝历史。
14. 时间平时自动推进，遇到需要玩家决策的事情暂停，玩家也能主动暂停处理政务。不采用逐日安排皇帝日常的玩法。
15. 内部需要合理的计算机制，支持跨时段推进；玩家不必操作每天的事务。具体计算方法尚未确定。
16. 允许大胆尝试改革、发展技术、改变制度与历史路径，提高自由度。具体行动范围与实现条件继续讨论。
17. 外交与战争和内政、朝局同等深入，以真实的皇帝体验为目标；不将外交、战争仅作为内政事件的背景。
18. 产品偏向数值模拟器，不追求强烈的画面表现；重点认真设计 UI，必要时使用插画。
19. 一局长期存档、慢慢经营，不要求快速节奏，也不设置必须在几小时内经历一段统治的设计目标。
20. 新开局允许适度随机变化，避免游戏变成固定流程；具体变化范围与幅度待设计。
21. 第一版同时交付本地网页游戏与 Android APK。网页端打开页面即可游玩；若需要运行环境、本地服务或较复杂的构建步骤，可以提供启动入口，简化使用。
22. **玩家负责皇帝层面的关键决策与审阅，执行细节交给各级官员。** 不要求玩家具备各部门的专业知识，也不让玩家逐项配置查账、运输、生产或作战的具体步骤。
23. 京城失守或丢失大片国土后，允许迁都、经营残局，并跨几代人尝试恢复。只要皇室仍有能实际运转的政权，就不因一次重大失败直接结束游戏。
24. 文案采用容易理解的白话，保留称谓、礼仪与人物语气，不追求浓重的半文言；操作按钮直接说明行动。
25. **从开局起经过 300 个游戏年，玩家仍未失败即判定胜利，并生成本局数据统计。** 从 1582 年开局，对应到 1882 年的开局日期达到目标；具体开局月日与游戏历法尚未确定。
26. **结算时可以向玩家揭示真实数据，让玩家了解实际治理效果。** 正常游玩期间仍不公开后台真值；结算是明确的信息边界例外。
27. **皇帝被权臣架空不直接算失败，允许继续寻找机会夺回实权。** 以可玩皇室政权被正式取代或再无可接续的皇室政权作为失败边界；正常的皇室继位不属于这种取代。具体分裂与角色转接规则仍需细化。
28. **以手机竖屏游戏为主要界面形态，方便移植。** 桌面横屏效果图已作为探索稿保留，不作为后续实现目标。
29. 为皇帝和各个关键臣下制作人物形象，增强代入感。具体画风与首批画像尚待用户看图反馈，不以外貌或配色暗示忠奸。

尚未确认具体开局日期、开局已知信息、继承细则、具体 UI 布局与人物画风、模拟粒度、随机变化的范围和技术栈。已确定手机竖屏优先，第一版交付网页与 Android APK。

### 玩家信息边界（对已确认原则的落实）

- 正常游玩中的所有玩家可见界面沿用皇帝视角，包括奏报、地图、人物面板、选项提示和处理结果；不能换一个界面就看到隐藏真值。终局结算按已确认规则开放真实数据。
- 人物可以指控某人贪腐或称赞某人忠诚，但必须明确是谁的说法，不能变成系统认证的人物属性。人物说法本身也可能有误或带有目的。
- 不用红绿颜色、真假图标、可疑标记、提示音等形式暗示系统已经知道的真伪；信息来源与原文可以保留，判断交给玩家。
- 系统可以组织和检索已收到的奏报，不能替玩家作出“此人撒谎”“该地腐败严重”等判断；辅助阅读的具体形式仍待讨论。
- 选项只描述皇帝要采取的行动，不预告“腐败度下降”“忠诚度增加”“查出贪污概率”等隐藏结果。臣下可以提出有归属的预测或劝告。
- 不能因后台已知存在贪污，才出现“调查”按钮；类似选项的出现条件应来自玩家已知的情境、权限或主动选择，避免通过按钮和禁用理由泄露真相。
- 不把某一种调查渠道设计成必定揭晓真值的工具；亲眼所见也只覆盖皇帝实际看见的范围，不自动扩展成全国实况。
- 开发调试需要的内部状态与玩家正常流程隔离。已确定结算时公开真实数据，帮助玩家判断实际治理效果；不能通过正常游玩中的统计或回顾页面提前开启这类信息。

## 二、核心体验假设（建议，待确认）

玩家需要判断：发生了什么，谁的说法可信，现在该问谁，以及在尚未弄清真相时要不要行动。

一个候选循环是：

收到奏报与官员建议，或主动提出方向 → 审阅、召见与追问 → 作出关键批示、任免或要求再议 → 官员拟定并执行细节 → 审阅回报，决定继续、调整或问责。

调查应花费时间和资源，也可能暴露皇帝的关注、影响当事人的行为。保留判断和选择的空间，避免变成必须逐条核验所有奏折的重复劳动。

基于用户选择的候选机制：皇帝可以勤政、委托事务，也可以减少过问。世界仍然继续运行，代理者的决策和对消息渠道的控制逐步产生后果；具体如何实现尚未确认。

### 皇帝决策与官员执行（操作层级已确认，流程细则待确认）

皇帝的主要操作是定方向、决定轻重缓急、任免主要负责人、批准或否决重要方案、要求解释与重新议定，以及审阅结果后调整或追责。可以主动要求提出新方案，不必永远只能接受眼前大臣列出的建议。

查哪些账簿、如何组织核验、怎样安排运输和生产等执行细节，由官员根据职责、能力、所知信息和自身利益决定。底层仍模拟这些过程；简化的是玩家操作，不是取消执行过程和执行偏差。

建议日常事务按既有制度与授权持续办理，只有重大取舍、重要任命、需追加授权的事项及玩家主动关注的问题进入关键决策。具体呈报筛选与权限规则尚待设计；筛选也可能受到官员利益影响，不能成为系统全知挑出的“真正重要事件”。

官员提出方案时，呈现其理由、声称需要的钱粮、预期效果和其他人的异议，均保留说话者与材料来源。系统不标注最佳方案、真实代价或成功率。实际执行超出授权、出现新困难时，可能再次请示，也可能自行应付或隐瞒。

丰富预设文案主要用于不同立场的建议、追问回应、执行中的请示及后续回报；不靠让皇帝填写大量专业参数增加操作量。关键决策也不会必然只有两个固定选项，具体选择依据已知局势和人物建议形成。

## 三、信息与执行的因果链（建议，待确认）

### 世界实际发生的事

模拟需要能够产生有因果关系的状况，例如粮食短缺、财政压力、军队补给不足。具体需要模拟到省、府、县还是个人，尚未确定。

底层真实状态供模拟运转使用，不能直接作为玩家可见面板。已经确认不显示系统置信评分或真伪提示。建议玩家可见数值保留来源、统计时间和统计范围，供玩家自己比较。

建议区分三类记录：实际状态、各级机构保管的账册、皇帝收到的呈报。地方账册本身也可能失真，没有哪个地方官天然掌握全部真实数据。中央汇总还可能沿用旧账、漏项或重复计算。三类记录都可以随时间变化，不能每次打开界面重新随机生成。

例如某仓账册记有十万石，实际只有三万石，送到皇帝手里的汇报仍称十万石。这组数字仅用于说明机制，不是历史数据或正式数值。差额应能由过去的出入库、实际损耗及未入账事项解释；底层无需提前替皇帝标出原因。

### 人们各自知道的事

不同人能接触的事实不同。官员可以诚实但判断错误，也可以为了保住职位、争取资源、维护关系或掩盖过失而选择性汇报。

是否说真话不能仅由一个固定“忠诚值”决定。同一个人可以在不同事情上采取不同做法。多份相同奏报也可能来自同一条消息，不能自动算作互相印证。

### 皇帝收到的说法

信息经过观察、整理、传递和筛选，最终才来到皇帝面前。延误、遗漏、误解和人为修饰都应尽量有具体原因，而非给每份奏报随机添加谎言。

皇帝可以获得新证据，但新的调查渠道也有成本、局限和自身利益。哪些渠道符合选定年代，需要后续史料核实。

### 命令实际产生的效果

一道旨意应通过人和组织执行。理解偏差、资源不足、拖延、抵制和变通都可能改变结果；最终回报也未必完整。

因此，设计不仅需要回答“皇帝知道多少”，还需要回答“皇帝说了算到什么程度”。

### 衰落如何产生

候选因果链：呈报充足 → 皇帝据此调拨 → 实物或执行能力不足 → 地方挪借、加征或拖欠以应付 → 后续生产与执行能力受损 → 下一轮缺口扩大，而呈报仍可能保持正常。

这是游戏机制假设，不是对明朝灭亡的单一历史解释。建议让人口、生产、财政、运输、军事、制度与外部冲击共同产生变化，不设置随年份必然下降的“国运值”。既然允许改变历史，治理改善应能改变走向，查出一份假账也不应自动解决所有结构问题。

### 数值合理性的候选约束

- 实物流转有账可核：期末库存 = 期初库存 + 实际入库 − 实际出库 − 实际损耗。银、粮分别记账，交易采用对应时间与地区的价格，不能无条件等价转换。
- 被侵占或转移的资源记录去向；报告被修改不会凭空增减真实库存。实际损耗也不能再作为贪污重复扣减。
- 区分应征、实征、留用、起运、在途与实收；区分命令、拨付与到达。内部调拨不能被全国汇总重复算作新增收入。
- 粮食生产遵循季节，运输受距离与运力约束，兵员受人口、补给和训练约束。缺粮与欠饷积累出后果，不以任意百分比立即降低所有数值。
- 人口迁移在迁出地与迁入地对应记录；支出受实际资源与可动员能力约束，缺口记为欠款或未完成任务，不能把负库存直接归零来掩盖错误。
- 报告记录来源、地域范围、事件时间、统计时间和送达时间；比较数字之前区分统计口径与时间差，不能把所有差异都视为舞弊。
- 史料中的数字也要区分账面数、估算数与可核实的实物数；不把历史奏报直接当成模拟底层真值。缺乏证据的参数明确记为假设，并在合理范围内校准。
- 开发验证可检查底层账目、异常路径与长期模拟结果；玩家界面显示什么仍由视角规则决定。合理基线不应无故崩溃，极端政策也不应无限创造资源。

以上是待讨论的数值设计约束，尚未确定具体参数、时间步长或实现方案。

### 预设文案与系统选择

交互形式和文案口吻已经确认；具体内容组织方式仍是建议。

奏报与对话使用清楚易懂的白话，保留称谓、礼仪和不同人物的表达习惯。按钮直接写行动，例如“准许先行接济”“责令查明”“交由廷议”。

用户认可的口吻示例（虚构，仅作语言尺度参考，不是史料或固定剧情）：“陛下，军饷虽已拨出，边镇尚未收到。臣请先筹款接济，再查延误缘由。”

按已确认的信息边界，文案中的主张归属于说话者，不能借旁白、语气提示或按钮说明认证真伪。人物可以表达犹豫、愤怒或笃定，但这些表现本身不等于真假结论。

每件政务由具体局势触发，预设文案按当事人知道的信息、所持立场和此前决定选择变体，并填入对应奏报的数据。文案中的数字取自该份报告，不直接读取底层真值，也不随世界变化篡改旧奏折。

选择可以分为批准或驳回方案、追问理由、要求再议、交办核查、任免及暂缓等类别，按权限与当前情境出现。每个选择必须对应真实的后续执行与反馈，不能只切换一句台词。

候选的追问示例：“为何与上次呈报不符？”“此法的钱粮从何而来？”“还有何人持不同意见？”这是现代语言的操作说明，最终历史措辞和对应制度需另行核实。玩家可以审阅具体材料，但不需要亲自设计专业核验步骤。

丰富度来自事项类型、人物立场、证据组合及持续后果的结合，并配合人工编写的关键事件。文案数量、变化幅度和首版范围尚待确定。

### 时间推进与内部计算（体验已确认，计算方案待确认）

玩家不逐日排班，也不需要逐条批准重复的日常事务。候选方案是由持续运转的经济与行政规则产生变化，再按时点处理命令、消息、运输和关键事件；平静时段可以快速经过，不能靠跳过时间来跳过后果。

- **暂停依据皇帝接触到的事情。** 地方发生隐秘事故时，世界继续变化；消息抵达皇帝、有人求见或皇帝亲历相关情况，才可能触发玩家决策。不能因为后台出现严重问题就立即暂停并暴露其存在。假警报和夸大的急报同样可能要求皇帝处理。
- **区分各阶段时点。** 事件发生、当地发现、呈报发出、宫廷收到、皇帝下令、地方接令、实际执行、回报抵达各有时间，不能在一次选择后同时完成。
- **按实际过程计算。** 生产随季节，消耗随经过时间，运输随路线与运力，征收和发饷随制度周期；统一推进世界时间，不要求所有子系统采用相同结算频率。
- **关键变化先结算。** 如果库存将在下一封消息到达前耗尽，就先处理耗尽及其后果，再继续推进；不能在月底一次性扣粮而漏掉月中断粮。未被皇帝得知的变化只在内部处理。
- **速度不改变规则。** 暂停阅读不推进游戏时间；已下达的命令仍需在恢复推进后等待执行。相同初始状态、随机种子与带时间的命令序列，在不同显示速度下应得到一致结果，存读档不能重复执行命令或重新抽取同一事件。
- **主动行动也有时长与承载限制。** 暂停时可以查看旧报与下达命令，但召见到场、查账、运粮等不会因暂停而瞬间完成。具体能力上限与限制形式待设计，不先设任意行动点。
- **控制重复打断。** 可以整理例行呈报、设置玩家关心事项的提醒；提醒只能依据收到的内容、玩家安排的期限与可见进度，不按隐藏的真实危害或腐败程度决定提示。具体筛选与委托方式待讨论。

计算方案后续需通过库存守恒、消息先后、跨季节推进、并发命令和多年演化等验证；当前尚未实现或选定时间步长。

### 继任者与世界连续性（延续游玩已确认，细则待确认）

建议换皇帝时保留地方人口、财产、账册、官员、债务、未完成命令和在途消息；继位不重置国家，也不自动揭晓上一任不知道的真相。

继任者的经历、亲信与实际影响力可以不同于前任。皇帝个人关系如何变化、档案如何交接、幼主或继承争议如何处理，尚待讨论，不默认套用历史上的固定结果。

玩家本人记得上一任经历，系统无法抹去这部分记忆；设计上需要承认这一点，通过继任者的权限、人际关系和可接触材料体现角色差异，而不假装能让玩家失忆。是否保留全部旧奏报及未读密件，另行确定。

### 重大败局后的延续（方向已确认，细则待确认）

已确认：京城失守、大片国土丢失或一次重大军事失败不自动触发终局。皇室仍有能实际运转的政权时，允许迁都、继续治理现有地区，并在继承后延续恢复目标。

候选实现需要保留败局的实际后果：失去的税源、交通与档案，仍可联系的官员与军队，以及迁移中的钱粮和人员。迁都不能自动搬走全部资源，也不能重置债务、地方问题或恢复实际控制力；皇帝只能通过可接触的消息逐步了解局势。

已确定允许残局延续，并以开局后存续满 300 个游戏年且未失败作为胜利条件。被权臣架空不触发失败；可继续争取实权，直到可玩皇室政权被正式取代或再无可接续的皇室政权。正常继位、失去京城以及已有可延续皇室政权的退守，仍按已确认规则继续。

被俘或废黜后的角色转接、多名继位者并立时的玩家身份，以及如何识别政权被取代和仍可接续的具体情况，仍待细化。不能把“实权低于某个隐藏分数”直接作为失败开关。

架空状态的候选表现包括：奏报或召见受到阻碍、任命遭到拖延、命令未被执行，以及他人要求皇帝追认既成决定。玩家通过实际遭遇判断自己的处境，不显示“已被架空”评分或夺权成功率。有哪些争取支持与恢复权力的关键选择，由后续人物和权力机制确定，不要求玩家操作具体行动细节。

### 胜利条件与本局统计（目标及真实数据公开已确认，展示细则待确认）

胜利以从开局开始经过的游戏时间计算：存续满 300 年且尚未失败，即判定胜利并提供统计。1582 年开局对应 1882 年达到这一目标，具体日期在开局日期和历法确定后落实。继位、迁都与政权退守不重新起算 300 年，存读档不改变已累计的时间。

这一目标不额外要求恢复某个疆域、达到某个财政数值或取得统一评价分数。重大失败后只要仍满足可继续游玩的政权条件，仍可走向胜利；完整失败判据需后续定义，不能用隐藏的“国运低于阈值”替代具体政权状态。

统计候选内容包括：本局历时、历任皇帝与在位时间、玩家作出的主要决策、迁都与继承记录、重要改革、战争与外交事项，以及真实人口、钱粮、生产与控制范围的历年变化。各字段需以实际实现的模拟和保存记录为依据，当前不承诺尚未定义的数据项。

已确认结算公开真实数据。候选展示方式是将真实状态与玩家当时收到的奏报、军报和账面数字并排对照，标明统计范围、数据时点、呈报来源和抵达时间，不能把不同日期或口径的差异自动算作瞒报。

候选复盘可以沿关键决策展开：皇帝当时知道什么、批准了什么、官员实际如何执行、真实结果如何、后来又报告了什么。对误报、遗漏、舞弊和传递延误的解释需来自模拟中的具体记录；缺乏记录的部分明确为未知，不能为了戏剧效果编造幕后动机。

治理结果与单项决策的因果贡献需要区分：同一时期的人口、财政或战局变化可能受多种条件共同影响。用实际执行链与结果解释，不将曲线变化全部归功或归咎于某次批示，也不把内部抽象评分冒充真实的社会事实。结算具体字段和是否有综合评价尚未确定。

胜利结算统计已经确定；提前失败是否采用同样完整的统计版式、胜利后能否继续经营，以及玩家看过真相后继续游玩的规则，仍待讨论。结算应基于存档中的可追溯记录，不能临时虚构历史或重算出与本局经历无关的结果。不能为了展示真相改写游戏期间保存的旧奏报。

300 年目标带来的候选设计要求：人口与资源长期变化有依据；官员与统治者有代际更替；技术、交通、军事、制度和外部势力能够随条件演变。需验证跨代、长期存档和长时间运行的一致性。具体时代演化内容与参数尚未设计，不把现实历史事件按年份强制发生。

### 改革与技术发展的自由度（方向已确认，机制待确认）

允许尝试超出原有历史走向的制度与发展路径。皇帝可以提出改革目标，命官员议定方案，并对负责人、重要资源安排、先试行还是全面推行等关键取舍作出批示。具体筹办步骤和实施办法由官员负责；玩家审阅建议与回报，决定批准、要求再议、调整或撤回。均通过预设选项操作，不依赖自由输入或大模型理解命令。

候选约束是知识、人才、财政、材料、生产条件、行政能力与利益冲突。皇帝提出目标后，要有人形成办法并实际执行；不能只支付一个数值就立即获得全国生效的制度或技术效果。也不因真实历史上未成功，就预先禁止玩家尝试。

技术发展可经历引入知识、试制、检验、扩大生产和维护等阶段。试验报告与生产账目同样可能失真；某次样品成功不意味着各地已经能够稳定制造。具体技术范围、现代知识边界和先决条件待讨论。

改革的反应建议根据具体利益和执行条件生成：同一措施可能得到部分官员支持、被另一些人拖延或变通。不要把阻力简单设为固定改革惩罚，也不把所有失败都解释为贪腐。

### 外交与战争（深度已确认，机制待确认）

目标是与内政、朝局同等深入，而非预先承诺所有系统采用相同数量的界面或相同模拟粒度。以下为实现这一目标的候选机制。

- **外交对象有自身处境。** 外部政权或集团具有自己的资源、内部利益、情报与目标，会主动谈判、备战、试探或改变策略。其真实意图不直接显示为好感度或开战倒计时。
- **外交通过人执行。** 皇帝决定目标、主要使臣和重大条件，审阅谈判建议与结果；具体交涉由使臣负责。使臣往返需要时间，可能误解、夸大或隐瞒。对方承诺与实际履约分开记录。
- **军事决策从皇帝权限出发。** 任将、规定战略目标、批准重大钱粮与兵力安排、授予临机处置权，以及决定战和，均须经过现实执行过程。具体征发、运输与战术由官员和将领负责，不能通过即时操纵远方部队绕过他们和军报。
- **军报与战场分离。** 呈报名册不等于实到兵员，实到兵员也不等于能够作战的人数；双方兵力、位置、损失和战果以皇帝收到的消息呈现。地图不直接更新后台实时位置。
- **战争影响内政。** 征发、运输、军饷、地方生产和人口变化相互作用；战果不直接换算成稳定的全国收益，停战后仍可能留下欠饷、驻防和地方秩序问题。
- **内政影响外交与战争。** 财政、运输、任官和朝内争议改变可供执行的战略，外交取得的通路或安排也可能影响贸易与供给，具体制度需按历史背景核实。
- **历史事件随条件发展。** 建议将历史作为初始局势与行为依据；此后战争与协议按参与者处境和玩家行动演变，不按固定年份强制恢复原有历史结局。

各方行为使用规则与预设内容表达。当前尚未确定战斗计算、外交行动清单、地域覆盖、势力数量或第一版的验证情境。

### UI 与长期存档（方向已确认，细则待确认）

以清晰、耐用的 UI 支撑长期数值模拟，插画按人物、场景或重要事件的需要补充。数值模拟器的定位不改变信息边界：底层数值用于运行世界，玩家界面中的数值仍来自呈报、见闻和可接触的记录。

手机竖屏是已确认的主要形态。候选布局以一件政务的阅读与批示为中心，相关呈报按需展开，底部提供触控操作与导航；不能直接缩小桌面多栏界面。皇帝头像用于身份代入，关键人物的具名头像或立绘用于召见、议政与呈报出处，具体布局以本轮效果图反馈为准。

已生成[首批人物形象概念](design/characters-v1.md)：万历、张四维、申时行、冯保与戚继光。这是人物画风样本，不是完整人物名册或已经完成的全套游戏资产；具体容貌、冠服及配套台词不作为史实复原。

建议围绕收到的政务、人物来往、旧奏报、已发命令和舆图组织界面。玩家可以按人物、地区、事项与日期检索、并排阅读原文、收藏材料、关联事件；系统不替玩家判断真伪或标注隐藏关系。

长期游玩需要能接续上次思路。候选功能包括未办事项、此前批示、约定回报日期与玩家自己的标记；回顾内容只引用已经获得的材料，不在读档时泄露离开前尚不知道的事情。“已下令”不能自动标为“已办成”，“未收到回报”也不能自动标为“执行失败”。

存档应完整保存世界状态、账册与报告版本、历史批示、未完成命令、在途消息和随机过程的状态，使跨皇帝、跨多年继续游玩时保持因果连续。自动存档、手动存档、备份与版本兼容方案待设计，当前尚未实现。

慢节奏意味着允许深入追查、等待长期结果和逐步经营关系，不用增加重复点击或让玩家在现实中空等。沿用已确认的时间推进方式，平静时段可以快速经过，玩家决定何时继续推进。

建议关闭游戏时停止模拟，重新打开后从保存的游戏时间继续，而不是根据现实离线时长推进帝国。此离线规则属于候选建议，尚未由用户确认。

### 适度随机变化（方向已确认，范围待确认）

建议固定已核实的历史背景和开局前事实，在史料不能确定的地方隐情、局部资源差异、办事反应与后续偶发事件上设置合理变化。不能为增加重玩性而任意改变确证的历史事实，也不简单把历史人物随机分配成忠臣或奸臣。

随机生成的初始状态需要彼此一致：人口、生产、税源与库存相互约束；亏空有来由，账册与呈报的差异有相应形成过程。不能独立抽取所有数值后拼成互相矛盾的世界。

同一局中已经形成的事实、账册和报告持续保存，只因后续实际行为而改变；打开页面、重复查阅或读档不能重抽既有真相。后续随机变化也应通过事件产生并留下后果。种子与随机状态随存档保存的技术细节待实现。

变化不能成为针对玩家的暗中改答案：玩家调查可能引起串供、补账等行为，但必须由人物获知调查、具备机会并采取行动产生，不能为了维持悬念直接替换过去的事实。合理差异的幅度和历史资料不足部分需单独标明。

### 网页与 Android APK 交付（双端已确认，技术方案待实现）

第一版必须包含本地网页与 Android APK，两端采用手机竖屏的主要交互。候选实现尽量共用模拟逻辑、内容与 UI，再处理存储、生命周期、返回键和安全边距等平台差异；具体框架、封装方案、后端需求与构建方式尚未选择。

当前视觉讨论稿为[手机竖屏主界面 v1](design/mobile-screen-v1.md)，已加入皇帝与阁臣头像；等待用户反馈，不代表正式 UI 已确定，也不是可运行游戏。桌面探索稿保留在设计目录中，但已标明不再是实现目标。

候选启动体验：用户双击入口 → 检查必需环境与现成构建 → 必要时启动仅供本机访问的服务 → 服务就绪后打开游戏网页。重复启动应复用可用实例，避免重复服务；出错时说明可采取的处理办法。正常游玩不应要求用户手工输入命令或每次重新构建。

长期存档的候选要求：保存在明确且稳定的本地位置，支持导出或备份；升级程序与重新构建不能覆盖已有存档。具体采用浏览器存储还是本地文件需结合架构确定，不能先承诺尚未实现的存储方式。

后续网页交付验证需从启动入口实际进入页面，检查新建游戏、保存、关闭后重开、读档继续及重复启动；APK 需实际安装并启动，在 Android 设备或模拟器中验证竖屏触控、返回键、后台恢复与存读档。若计划 APK 独立离线运行，还须验证它不依赖开发电脑上的服务。双端存档导入导出与兼容策略待确定。当前仓库仍处于设计阶段，尚无可运行游戏、启动入口或 APK。

## 四、用于讨论的体验例子（虚构，不是史实或已确认剧情）

某地上报受灾有限，粮食仍足。另一份消息却说当地粮价上涨，附近驻军又报告买粮困难。

这些说法未必只能解释为官员贪腐：可能统计滞后，可能几个地区受灾程度不同，也可能粮食存在但运输受阻。

玩家可以先赈济、要求补报、召见相关人员，或派人查验。每个选择都会花时间、消耗资源并改变局势。理想的体验是玩家能提出假设、找到线索并承担选择，而不是只能猜测幕后随机答案。

## 五、优先讨论的问题

### 第一轮：身份与日常（已回答）

1. 身份方向：真实历史节点开局，之后允许改变历史；具体起点见第三轮已确认内容。
2. 日常：奏折与召见两者都重，允许自己选择怎样当皇帝。

### 第二轮：衰落节点与交互（已回答）

1. 开局局势：从鼎盛走向衰败的时间点开始。
2. 交互：丰富的预设文案与系统选项；不采用自由打字或运行时大模型对话。
3. 核心强调：皇帝拿到的数据本身就可能与地方实际数据不符，数值体系需要合理。

### 第三轮：开局与信息边界（已回答）

1. 接受 1582 年张居正去世后、万历亲政开局。
2. 系统不作面向玩家的真伪判断，不暴露腐败度或可信度等隐藏信息。内部是否采用评分留给后续设计。

### 第四轮：继承与时间推进（已回答）

1. 皇帝去世后允许继续扮演继任者。
2. 平时推进时间，遇到决策暂停，允许主动暂停；不用模拟每天日常操作，重点保证内部计算合理。

### 第五轮：改革自由度与内外政范围（已回答）

1. 允许大胆尝试改革和不同的发展道路，以获得更高自由度。
2. 外交、战争与内政、朝局同等深入，追求真实感。

### 第六轮：表现形式与单局节奏（已回答）

1. 偏向数值模拟器，UI 认真设计，必要时配插画，不追求强画面表现。
2. 一局慢慢玩、长期存档，不要求快速节奏。

### 第七轮：随机变化与交付平台（已回答）

1. 可以有适当随机变化，避免变成固定流程。
2. 确认本地网页与可选启动入口；当前交付范围已扩展为第十三轮确定的网页与 APK 双端。

### 第八轮：皇帝的操作层级（已回答）

1. 皇帝负责关键决策与审阅，不需要操作过细或掌握各项专业细节。
2. 各级官员负责具体执行。此前过细的调查与命令配置建议已收束为官员执行过程。

### 第九轮：重大败局后的延续（已回答）

1. 接受京城失守或大片国土丢失后继续迁都、经营残局，跨几代人尝试恢复。
2. 皇室仍有实际能够运转的政权时，不因一次重大失败直接结束。

### 第十轮：文案口吻（已回答）

1. 接受易懂的白话奏报与对话，保留称谓、礼仪和人物语气；此前军饷示例的古意程度足够。
2. 操作按钮直接说明行动，不需要更浓重的半文言。

### 第十一轮：胜利目标与统计（已回答）

1. 开局后经过 300 年，玩家还没有失败即算胜利。
2. 胜利时做本局数据统计。
3. 用户进一步确认：结算时可以暴露真实数据，让玩家知道真实治理情况；具体字段与展示方式待设计。

### 第十二轮：被架空后的延续（已回答）

1. 接受皇帝被权臣架空后继续游玩，寻找机会夺回实权。
2. 失败边界为可玩皇室政权被正式取代，或再无可接续的皇室政权；与已有继承和退守延续规则保持一致。

### 第十三轮：竖屏与人物视觉（已回答，效果图待反馈）

1. 改为手机竖屏游戏形态，方便移植。
2. 第一版同时提供网页和 APK 两种形式。
3. 制作皇帝及关键臣下的形象以增强代入感；当前已生成首批概念合稿和带头像的竖屏界面。

### 开局的历史依据与待核实范围

故宫人物资料记载，1582 年（万历十年）张居正去世，万历亲政。这是已选定的起点，**不是万历即位年份**。来源：[故宫博物院·张居正](https://www.dpm.org.cn/court/figure/104014.html)。

历史节点已核实；财政库存、地方人口、军队规模、官员关系以及皇帝开局能够接触的消息仍需收集并交叉核对资料。不能用当前人物简介推导精确的经济初始值，也不能把人物的后世评价直接呈现为玩家可见属性。

### 下一轮及后续问题

- 时代与开局：1582 年内的具体日期、初始局势与已知消息、历史事件的发生条件。
- 随机细则：适度随机变化的具体对象、相关约束与幅度，如何保留历史依据和同局因果连续性。
- 角色与继承：继任者的人际关系、权限与档案交接，幼主或继承争议，以及是否允许玩家带入现代知识。
- 时间与处理能力：消息与命令的时延、主动召见和调查的承载限制、例行政务筛选与委托。
- 信息体验：在不替玩家判断的前提下如何呈现来源与旧奏报；地图与人物档案如何保持皇帝视角。
- 决策细则：哪些取舍需要皇帝批示、哪些由官员自行处理；方案如何提出、筛选、再议与回报。
- 改革细则：具体改革与技术目标、现代知识边界、知识与人才等实现条件、官员如何拟案与执行。
- 外交与军事细则：参与势力、谈判授权、战争目标、将领自主权、军报与后勤模拟。
- 人物行为：利益、能力、关系、恐惧如何影响判断与执行；预设文案与选项如何呈现这些差异。
- 真实性与可玩性：细节模拟到什么层级，哪些可抽象，如何避免重复批奏折。
- 失败与结算：被俘、废黜与政权分裂后的角色转接，识别正式取代与可接续政权的具体规则；结算真实数据与呈报的对照字段，是否允许看过真相后继续。
- 长期演化：1582 年至 1882 年期间技术、制度、人口、代际和外部势力如何随条件变化。
- 文案内容：按已确认口吻编写人物表达差异、政务变体与后续回报，避免语气或旁白泄露真伪。
- 历史依据：确定年代后核实制度、职官、奏报渠道、财政与军事规则，并记录来源和不确定性。
- UI 与存档：具体信息布局、检索与接续游玩、存档备份与兼容、关闭游戏后的时间规则。
- 原型与交付：手机竖屏网页与 APK 的首个可玩情境、最小模拟范围、共用架构、启动入口、Android 打包与双端存档落地方式。
